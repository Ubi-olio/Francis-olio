我们通常把 AI Agent 的能力归结于模型：模型越强，任务应该完成得越好。

但使用过编码 Agent 就会发现，失败有时并不发生在「想不出答案」这一步。它可能找到了正确文件，却一直重复阅读；可能知道应该运行测试，却提前宣布完成；也可能在连续调用工具时丢失工作目录，随后围绕错误的环境不断尝试。

这些问题让人开始重新审视：**模型的能力，究竟如何才能转化为可靠的任务执行？**

<!-- more -->

[《Harnesses That Improve Themselves: A Unifying Framework for Self-Improving Agent Harnesses》](https://arxiv.org/html/2611.22299v1)关注的正是这个问题。作者将目光放在模型周围的运行软件上，讨论如何根据执行失败，自动改进 Agent 的工作方式。这篇工作的主体是一套统一的架构与设计框架，并通过小规模编码实验检验其中的设计思路。

## 从「模型会不会」到「系统能不能完成」

先想象一个简单任务：让 Agent 修复博客中的模板错误。

模型需要阅读模板、判断原因、修改代码，然后运行构建。构建失败时，它还得根据错误继续调整。

在这个过程中，模型负责推理和生成操作，而另外一层软件负责组织整个执行过程：

- 每一轮给模型提供哪些信息；
- 如何执行文件修改和终端命令；
- 如何保存任务状态与工具反馈；
- 遇到重复失败时是否继续尝试；
- 满足什么条件才允许结束。

这层软件就是 **agent harness**，可以理解为 Agent 的运行框架。

它连接模型与实际环境。模型提出操作，框架负责执行，再把结果整理成下一轮的输入。一项长任务，就是这样被拆成连续的交互。

因此，当 Agent 最终失败时，需要检查的不只有模型的推理能力，还有这条执行链路。

## 自我改进，具体改什么？

这里的「自我改进」很容易让人联想到模型训练：收集数据、更新权重，让模型学会新的知识。

这篇论文讨论的重点是另一条路径：**保持模型权重不变，修改它运行时使用的软件。**

比如，Agent 总是在验证之前结束任务，可以修改结束检查；Agent 总是被大量旧日志淹没，可以调整上下文管理；Agent 反复执行同一条失败命令，可以加入重复检测与策略切换机制。

作者用四类组件描述这些可修改部分：[论文 §II](https://arxiv.org/html/2611.22299v1#S2)

| 组成部分 | 核心问题 |
| --- | --- |
| 上下文与状态 | 下一轮模型需要看到、记住什么？ |
| 执行控制 | 继续、重试、换策略，还是结束？ |
| 工具接口 | 怎样把模型的决定变成真实操作，并返回结果？ |
| 验证与恢复 | 怎样检查结果，失败后怎样继续？ |

从这个角度看，Agent 的进步可以来自更合适的信息组织、更可靠的操作接口，以及更清晰的完成条件。

## 两个循环：做任务，以及改进做任务的方式

整篇论文最容易理解的结构，是一个执行内环，加上一个改进外环。

执行内环处理用户任务：读取信息、生成操作、执行工具、检查反馈，再决定继续还是结束。

改进外环则查看这些执行记录，寻找反复出现的问题，提出框架代码补丁，验证之后决定是否保留。[论文图 1 与 §II](https://arxiv.org/html/2611.22299v1#S2)

下面是按这一关系整理的文字示意：

```text
使用现有框架完成任务
        ↓
留下执行记录与验证结果
        ↓
分析重复出现的运行缺陷
        ↓
修改框架代码
        ↓
验证并接受有效修改
        ↓
使用新框架处理后续任务
```

这意味着，一次失败除了产生任务结果，也可能提供改进系统的材料。外环提出修改的优化器可以使用另一个编码模型，也可以由同一个模型承担不同角色。

不过，关键在于判断：这次失败究竟暴露了什么？

## 先找对故障，再修改系统

下面用一个博客开发场景说明。**这个例子用于解释机制，并非论文实验。**

假设 Agent 修改了模板，随后直接告诉用户「已经修复」，但实际构建仍然失败。

最直接的做法，是补上一句提示：

> 修改之后，请先运行构建再宣布完成。

这条规则有帮助，但它仍然依赖模型在合适时刻记住并主动执行。

另一种做法，是修改框架的结束入口：收到完成请求时，检查最后一次编辑之后是否运行过构建，以及构建是否成功。没有有效证据，就把检查结果返回给模型，让任务继续。

这里，「最后一次编辑之后」非常重要。如果先构建成功，再修改模板，之前的通过记录已经不足以证明当前版本正确。

这个例子也揭示了框架改进的本质：**把某些容易遗漏的要求，变成运行过程中实际执行的约束。**

但并非所有失败都适合这样处理。如果工具执行正常、必要信息也没有丢失，模型却始终理解错业务逻辑，那么继续添加运行检查未必能够解决问题。轨迹分析需要先形成故障假设，再通过实验检验它。

## 我的想法

沿着论文的思路，我想借用软件工程中已经积累、广泛采用的实践，把需求澄清、测试、代码审查和故障复盘作为自进化 Agent 的初始流程。让它在执行中发现流程的不足，提出修改，再通过独立验证决定是否保留，或许就能让经验逐渐沉淀成更可靠的工作方式。这是我基于论文产生的设想；能否持续变好，还需要观察真实任务中的效果与成本。
